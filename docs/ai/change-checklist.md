# AI 修改检查清单

每次 AI 修改代码前后必须检查本清单。没有做到就不要声称完成。

## 修改前检查

- 是否理解用户需求？
- 是否确认用户要你直接修改，而不是只咨询？
- 是否找到相关文件？
- 是否阅读相关文件？
- 是否找到已有同类写法？
- 是否确认不会破坏旧 API？
- 是否确认不会修改公开路由、配置字段或数据结构含义？
- 是否确认不需要新增依赖？
- 是否确认不需要大重构？
- 是否确认当前目录和真实 Git 状态？
- TypeScript 任务是否阅读了 `docs/ai/typescript-guide.md`？
- 新增文件前是否阅读了 `docs/ai/project-structure.md`？

## 修改中检查

- 是否最小改动？
- 是否只修改任务相关文件？
- 是否没有使用 `any`？
- 是否没有使用 `as any`？
- 是否没有使用 `as unknown as Xxx`？
- 是否没有使用 `// @ts-ignore`？
- 是否没有滥用 `// @ts-expect-error`？
- 是否没有绕过类型系统？
- 是否没有乱建目录？
- 是否没有删除用户已有逻辑？
- 是否没有无意义重构？
- 是否没有引入未经要求的新依赖？
- 是否没有把后端模块直接 import 到前端组件？
- 是否没有把敏感信息写入代码、日志或响应？

## 修改后检查

- 是否运行了可用检查命令？
- 是否说明了没运行检查命令的原因？
- 是否检查了修改文件列表？
- 是否总结了修改文件？
- 是否说明了为什么这样改？
- 是否说明了是否影响旧功能？
- 是否说明了风险？
- 是否说明了用户下一步要做什么？
- UI 修改是否实际检查了可见效果？
- API 或数据库修改是否检查了兼容性？
- 没有验证的内容是否明确标注为未验证？

## 最终回复模板

必须包含：

```md
结论：已完成 / 未完成 / 部分完成。

修改文件：
- `文件路径`：用途。

验证：
- 已运行：`命令`
- 未运行：原因。

影响：
- 是否影响旧功能。
- 仍有什么风险。

下一步：
- 用户需要做什么；如果不需要，就写“不需要额外操作”。
```

禁止写“测试通过”，除非真的运行了对应测试或检查命令。
